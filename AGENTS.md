## Architecture

- **`MercVerified/Code/`** — Auto-generated by Aeneas; never edit manually.
- **`MercVerified/Code/*External.lean`** — Hand-written stubs for external functions (e.g. HashMap ops). Edit as needed.
- **`MercLib/`** — The Aeneas-independent library, split into layers. Namespaces follow the area, not the layer (`MercLib.ParityGame`, `MercLib.Sigref`, ...).
  - **`Util/`** — reasoning infrastructure (loop induction for `while`/`for` in `Id.run do`).
  - **`Theory/`** — definitions and theorems: `Graph` (SCCs), `LTS` (branching bisimilarity), `Signatures`, `Sigref` (abstract strong/branching signature refinement), `ParityGame` (games, attractors, fatal attractors, the Vöge–Jurdziński valuation), `Refinement` (trace/failures/impossible-futures semantics), `Rewriting` (conditional term rewriting).
  - **`Algorithms/`** — algorithms in pseudocode style, proved against the theory: `Graph/Tarjan`, `Sigref` (worklist, iteration, key computation, τ-SCC, topological sort), `ParityGame` (Zielonka), `Refinement` (antichain refinement checking), `Rewriting` (set automaton construction and matching).
  - **`Implementation/`** — models of merc's data structures, proved against the algorithms (`ParityGame/Implementation`).
  - In every area, the spec files are human-vetted (each headline claim a named `def ... : Prop`; make only minimal, targeted changes) and the `Proofs/*_Proofs.lean` files next to them are machine-generated (may be freely edited or regenerated). Headline theorems are re-stated with `sorry` in `Challenges/<Area>.lean` and checked by `lake comparator --config comparator.json`.
- **`MercVerified/Refinement/`** (for the `merc_refinement` crate) and **`MercVerified/Lts/`** (for the `merc_lts` crate; namespace `MercVerified.Lts`) — Human-vetted contract specs and definitions for the translated code (e.g. `Refinement/Refinement.lean`, `Lts/Lts.lean`) Each spec file states a claim as a named `def ... : Prop`, never a theorem; the headline theorems proving them are re-stated with `sorry` in the human-vetted comparator challenge `Challenges/MercVerified.lean` (solution module `MercVerified`, config `comparator_MercVerified.json`). Make only minimal, targeted changes.
- **`MercVerified/{Refinement,Lts}/Proofs/`** — Machine-generated proofs of the specs above. May be freely edited or regenerated. Each proved "headline" theorem is guarded against drift by its `sorry` challenge in `Challenges/MercVerified.lean`, checked by `lake comparator` (not in this directory). See the lean-conventions skill for the full spec/Proofs/challenge pattern.

## Skills

Task-specific instructions are skills in the Agent Skills format (YAML frontmatter with `name` and `description`, then Markdown). Before starting a matching task, read the skill file and follow it. When a skill refers to "the `X` skill", it means `.agents/skills/X/SKILL.md`.

| Skill file | Read when |
|---|---|
| `build` | Build and test commands |
| `regenerate` | Regenerate Lean code from Rust sources |
| `lean-conventions` | Lean 4 coding and proof conventions |
| `rust-conventions` | Rust coding conventions |
| `prove` | lean-lsp MCP workflow, tools, and key definitions |
| `ci` | CI workflow descriptions |
| `delegate-proofs` | Splitting proofs across `lean-prover` subagents and opencode instances |

## Agents

- **`lean-prover`** (`.claude/agents/lean-prover.md`) — Claude Code subagent for proofs that need a plan; edits only `Proofs/` files.
- **`prover`** (`.opencode/agents/prover.md`) — opencode agent for one routine lemma, launched by `scripts/delegate_proof.py`, which checks the result itself (statement unchanged, no `sorry`/axioms, `lake build` passes) and restores the file on failure. See the `delegate-proofs` skill.
