# merc-verified

Formal verification of labelled transition system (LTS) algorithms. Rust implementations in `verified` are translated to Lean 4 via [Aeneas](https://github.com/AeneasVerif/aeneas) and verified against formal definitions in `MercVerified/` and `Signatures/`.

## Architecture

```
verified           ← Rust implementation (source of truth for algorithms)
    └─ charon ──► *.llbc  ──► aeneas ──► MercVerified/Code/  (auto-generated, do not edit)

Signatures/      ← Formal LTS definitions and bisimilarity theory (hand-written)
MercVerified/    ← Proofs connecting generated code to specifications (hand-written)
3rd-party/       ← Git submodules: aeneas, merc (do not modify directly)
```

- **`MercVerified/Code/`** — Auto-generated by Aeneas. Regenerate by running Aeneas; never edit manually.
- **`MercVerified/Code/*External.lean`** — Exception: the `*External.lean` files (not `*External_Template.lean`) are hand-written stubs that implement external functions (e.g. HashMap ops) not handled by Aeneas. Edit these as needed.
- **`Signatures/`** — Hand-written: `Basic.lean`, `BranchingBisimilarity.lean`, `Signature.lean`, `InductiveSignatures.lean`, and `Proofs/` (proofs split out from definitions).
- **`lakefile.toml`** — Two libraries: `MercVerified` and `Signatures`. Dependency on `cslib` (leanprover) and `aeneas` backend.

## Build Commands

```bash
# Build everything (checks all Lean proofs)
lake build

# Build just the Rust crate
cd verified && cargo build

# Run Rust tests
cd verified && cargo test
```

## Regenerating Code from Rust

Run after changing `verified/` source:

```bash
# Step 1: Compile Rust → LLBC (produces verified/verified.llbc)
cd verified
../3rd-party/aeneas/charon/bin/charon cargo --preset=aeneas
cd ..

# Step 2: Translate LLBC → Lean (outputs to MercVerified/Code/)
./3rd-party/aeneas/bin/aeneas -split-files -backend=lean -dest=. -subdir=MercVerified/Code ./verified/verified.llbc
```

Then update `MercVerified/Code/*External.lean` to implement any new external function stubs.

## Lean 4 Conventions

- Toolchain: `leanprover/lean4:v4.30.0-rc2` (see `lean-toolchain`).
- `camelCase` for definitions and theorems; `PascalCase` for types and structures.
- Use `theorem` for propositions, `def` for computations. Prefer `structure` over nested `Sigma` types.
- Import from `Cslib` (e.g. `Cslib.Foundations.Semantics.LTS.Basic`) rather than reimplementing standard LTS theory.
- `Signatures/BranchingBisimilarity.lean` uses `public section ... end` and `public import` — follow this pattern.
- Keep proofs self-contained within their modules; avoid circular imports between `MercVerified/` files.

## Rust Conventions

- Edition 2024. `#![forbid(unsafe_code)]` is enforced.
- Keep code Aeneas-compatible: no `async`, no trait objects, no raw pointers, no features Aeneas cannot translate.
- `snake_case` for functions/variables, `PascalCase` for types.

## AI Agent Workflow (lean-lsp MCP)

The `.mcp.json` configures a `lean-lsp` MCP server for interactive proving. Key tools:

- `lean_goal` — proof state at a cursor position ("no goals" = done)
- `lean_diagnostic_messages` — compiler errors/warnings
- `lean_multi_attempt` — test a list of tactics at a position without editing
- `lean_local_search` — find local definitions before guessing names
- `lean_leansearch` / `lean_loogle` / `lean_state_search` — search mathlib/cslib

When writing proofs, use `lean_multi_attempt` to test tactics before committing edits.

## Key Definitions

| Symbol | File | Description |
|---|---|---|
| `LabelledTransitionSystem` | `Signatures/Basic.lean` | Core LTS structure |
| `LTS.IsBranchingBisimulation` | `Signatures/BranchingBisimilarity.lean` | Branching bisimulation predicate |
| `BranchingBisimilarity` | `Signatures/BranchingBisimilarity.lean` | Bisimilarity relation (`≈br[lts]`) |
| `StrongSignature` / `Refine` / `IsStable` / `FixPoint` | `Signatures/Signature.lean` | Partition refinement for observational equivalence |

## CI

Two workflows in `.github/workflows/`:

- **`lean_action_ci.yml`** — runs `lake build Signatures` to check the hand-written Lean proofs against the checked-in generated code.
- **`update_aeneas.yml`** — full regeneration pipeline (OCaml setup → build Charon → build Aeneas → generate LLBC from `verified/` → translate to `MercVerified/Code/`). Fails if the regenerated code differs from what's checked in, so commit the regenerated `MercVerified/Code/` after changing Rust sources.
